## 文档覆盖范围

完整方案按照“问题与约束—现状证据—方案和取舍—详细设计—验证—实施与回退”组织。必有的章节 id：

- `context`：需求版本、目标、非目标、已知约束和待补材料。
- `decisions`：真实选项、推荐、理由、条件和决策状态。
- `architecture`：上下文、组件职责、现状与新增、系统边界。
- `interfaces`：接口/事件契约、授权、错误、兼容与幂等。
- `data`：字段、键、约束、关系、索引、读写与删除。
- `reliability`：事务、并发、重试、部分失败、补偿与恢复。
- `security`：认证、对象授权、敏感数据、秘密与审计。
- `capacity`：参数来源、估算公式、目标与实测区别、观察指标。
- `testing`：正向、异常、并发与权限验证及完成定义。
- `rollout`：兼容迁移、回填、开关、发布停止条件和回退。
- `implementation`：变更位置、依赖、任务、角色、完成定义。
- `risks`：风险、触发条件、后果、处理、阻断项和待谁确认。

与具体需求无关的条目可写不适用并给理由，不能空白或用口号填满。接口、字段、代码示例可放 `code` 内容块，不必设计额外脚本。

## JSON 通用结构

根对象使用 UTF-8 标准 JSON，不允许重复键、NaN、注释或尾逗号：

- `title`、`original_request`、`summary`：非空字符串，原话不改。
- `status`：`探索草稿`、`待评审`、`已确认`。
- `sources`：非空对象数组，每项有 `id`、`title`、`note`，可选真实 HTTP(S) `url`。本地证据写路径、版本和符号到 note，不伪造 URL。
- `requirements`：上游需求数组，下文详述。
- `designs`：技术设计项数组，下文详述。
- `sections`：非空数组，每项 `id`、`title`、`blocks`；涵盖上述章节 id，编号不重复。
- `diagrams`：至少三个互补图、至少两种类型，并包含 architecture。小改动确需简化时可由 Agent 自行产出指定文档，不把不满足默认契约的数据塞给渲染器。

所有编号使用字母开头的英文数字和短横线；需求 `REQ-...` 至少三位数字，设计 `DES-...` 至少三位数字。页面锚点须全局唯一。

通用证据字段：`status` 必填，只能 `已确认`、`建议`、`待确认`；`source_ids` 必填数组，可为空，但已确认项必须有真实来源编号。`已确认`文档不能包含建议或待确认条目。工具只能检查引用存在，不能判断来源是否支持结论。

### 内容块

- `paragraph`：`type`、`text`、通用证据字段。
- `list`：`type`、非空 `items`；每项 `text` 和通用证据字段。
- `code`：`type`、`language`、`text`、通用证据字段。代码作为文字转义展示，不执行；语言说明用普通文字，不插入动态类名。

关键判断单独标状态；同一段同时有已确认现状和建议改造时拆两块。概要只描述整体方向，不能承载无标记的实施断言。

## 需求、设计与验证映射

每个 `requirements` 条目：`id`、`name`、`status`、`source_ids`、`acceptance`；acceptance 是非空字符串数组，保留上游可观察结果。整条规则和验收继承该需求状态。

每个 `designs` 条目：

- `id`、`name`、通用证据字段。
- `req_ids`：至少一个存在的需求编号。
- `responsibility`、`changes`：职责与拟变更，非空字符串。
- `inputs`、`outputs`、`failures`：非空字符串数组。
- `tests`：非空字符串数组，含前提、动作、可观察结果，不能只写“单测通过”。

所有需求必须被至少一个设计覆盖，所有设计必须指向已有需求。图可以引用设计与需求；测试位于设计条目内，构成可定位的 `REQ → DES → tests` 映射。文档确认状态不代表测试已执行。

## 研发图表字段

每张图都有 `id`、`type`、`section_id`、`title`、`caption`、通用证据字段、非空 `req_ids`、非空 `design_ids`。引用必须存在。section_id 指向实际章节，图在该章节内容后显示。

### 节点关系图

以下类型使用 `nodes` 与 `edges`：`architecture`、`flow`、`state`、`dataflow`、`deployment`、`dependency`、`swimlane`。

节点至少两个，每项：

- `id`、`label`、`detail`、通用证据字段。
- `kind`：`actor`、`process`、`store`、`decision`、`state`、`task`、`service` 之一，控制形状。
- 可选 `group`：层级、信任域、部署区或泳道职责名；在图中显示，不暗示自动构建隔离边界。

关系至少一项，每项 `from`、`to`、`label`、通用证据字段。端点必须存在，所有节点有至少一条边。不接受自环；用独立步骤或明确描述重试条件。图中 label 包含条件、协议或动作，而非“连接”。

`dependency` 要求无环。`swimlane` 要求每个节点有 group，图同时显示责任分组与明确工作流。部署 group 是逻辑示意，实例数、真实网络边界须正文有依据。

### 时序图 sequence

- `participants`：至少两个，字段 `id`、`label`、`detail`、通用证据字段。
- `messages`：非空有序数组，每项 `from`、`to`、`label`、`kind`、通用证据字段。kind 为 `request`、`response`、`event` 或 `note`；条件与失败写 label，事件用文字明示异步。

泳道式参与者横向排列，消息按数组顺序纵向绘制，支持同一参与者内部动作。每项文字自动换行。分支不是隐含的 UML alt 执行语义：为互斥或异常分支拆成单独图，或在消息条件和 caption 明确哪些路径互斥，不能顺序暗示所有条件都同时执行。

### 实体关系图 er

- `entities`：至少两个，每项 `id`、`label`、通用证据字段、非空 `fields`。
- fields 项有 `name`、`data_type`、`constraint` 三个非空字符串，如主键、外键、可空与唯一约束；没有确认值就标明候选。
- `relations`：非空数组，每项 `from`、`to`、`label`、`cardinality`、通用证据字段。cardinality 只能 `1:1`、`1:N`、`N:1`、`N:M`，表示 from 到 to。

基数作为明确关系标签渲染，不冒充自动检查外键存在；Agent 须核对字段、约束和正文契约。

## 校验与输出边界

check.py 验证结构、来源/需求/设计引用、覆盖、图端点、依赖无环、图种和状态，输出表达建议；0 为结构通过，1 为结构不合格，2 为读取/参数错误。仅只读，不改业务内容。

render.py 先验证后生成内联 CSS/SVG HTML，0 为生成成功，2 为错误；默认独占创建目标，`--force` 可更新。只处理纯文本，不执行 HTML/JS、代码块或外部素材；引用只允许合法 HTTP(S)。

渲染器便于离线文档，不是无限复杂图引擎。关系类图节点按纵向布局并用显式连线连接，分支和回边另分配路径；时序、ER 和泳道有专用布局。ER 将字段实体框与带基数关系图组合，详情不压缩成小字。大图应拆分，参考 diagrams.md。结构通过无法证明算法、业务、语义或视觉正确，交付前仍须真实检查。
