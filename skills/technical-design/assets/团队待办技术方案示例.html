基于团队待办到期提醒需求，写一份含研发图表的技术方案探索稿。

本例是虚构的单渠道提醒设计，不代表真实系统现状。建议复用待办与通知能力，用数据库任务记录调度、版本校验防止旧提醒，并将结果未知与发送失败区分；接口、容量和保存策略仍待确认。九种图仅演示技能能力。

需求与设计映射

REQ-001 保存提醒设置

建议
  • 给定用户可编辑待办，当保存有效设置，则可读回设置，冲突与失败不显示成功。

关联设计：DES-001

REQ-002 有效提醒才发送

建议
  • 给定到期任务，当待办已完成、版本失效或权限撤销，则取消，不发送待办内容。
  • 给定渠道结果未知，当恢复处理，则先对账或人工判断，不能盲目重发。

关联设计：DES-002

REQ-003 通知打开仍鉴权

建议
  • 给定历史通知，当用户权限已撤销，则不展示待办详情。

关联设计：DES-003

DES-001 设置与版本控制

建议

在设置写入时检查编辑权限与待办版本。

实施变更：拟扩展待办详情接口和提醒设置模型；现有文件与接口尚待读取。

输入

  • 待办标识、提醒时间、客户端看到的版本

输出

  • 保存后的版本或明确冲突错误

失败与恢复

  • 数据库失败则不返回保存成功；客户端保留输入。

验证标准

  • 给定同版本的并发修改，当只允许一个条件更新成功，则另一个返回冲突且不覆盖新值。

DES-002 调度、校验与发送结果

建议

领取有效任务、发送前复查权限与版本、记录渠道结果。

实施变更：拟增加任务表和工作器；数据库原子领取与租约策略须按实际数据库验证。

输入

  • 已到期且未处理的任务、当前权限与待办状态

输出

  • accepted、cancelled、failed 或 unknown 状态

失败与恢复

  • 发送后宕机可能无法确认结果，记录 unknown；渠道无幂等或查询能力时人工对账。
  • 领取竞争通过条件更新避免重复领取；租约失效和旧工作器恢复须核对版本。

验证标准

  • 给定两个工作器竞争，当同一有效版本被领取，则只有一方发送候选请求。
  • 给定渠道受理后响应丢失，当恢复任务，则标 unknown，不自动假设失败。

DES-003 通知入口权限复查

建议

通知跳转与待办详情再次进行对象级授权。

实施变更：拟复用真实详情访问链路，当前路由和鉴权代码待确认。

输入

  • 已登录用户、通知关联待办标识

输出

  • 授权后的待办详情或无权限/不存在提示

失败与恢复

  • 历史通知不携带可绕过授权的敏感详情缓存。

验证标准

  • 给定撤销成员权限，当从旧通知打开待办，则不能获得详情。

本期只做站内提醒

待确认 本文是探索稿。提醒时间、时区、延迟阈值、规模和渠道幂等能力待确认，不能据此直接上线。

先复用数据库与通知能力

建议 建议先采用数据库任务记录和工作器，减少额外中间件。备选消息队列适合更大规模，但会增加部署与一致性管理；当前没有规模依据，暂不推荐新增。数据库索引和领取语义须实测。

逻辑组件各自负责一种职责

建议 设置 API 负责权限与版本写入，工作器负责调度和触发前复查，渠道适配层只调用既有站内渠道。它们是候选逻辑职责，不代表必须拆为三个服务。

拟议接口明确成功与冲突

候选 HTTP 契约 建议 ；仅展示，不执行

PUT /todos/{todo_id}/reminder
请求：remind_at（带时区时间）、expected_version（整数）
成功：设置标识与新版本
失败：输入无效、无权限、不存在、版本冲突、服务不可用
幂等与错误码具体值：待真实接口风格确认

建议 打开通知走待办详情对象级授权；设置成功不等于通知已发送，渠道 accepted 不等于用户已读。

任务版本与发送结果分开保存

建议 建议提醒任务使用 todo_id 与 reminder_version 建立业务唯一约束，记录触发时间、租约、状态、attempt 标识与发送结果。唯一约束不保证外部通知恰好一次。保存期限、删除联动和审计访问范围待确认。

未知发送结果必须先对账

建议 领取和状态更新通过数据库条件更新完成，发送在事务外执行。数据库提交与外部渠道受理不能原子保证；响应丢失或发送后宕机会产生 unknown。只有渠道支持可靠幂等或查询时才按既定规则自动恢复，否则人工对账。

待确认 发送前复查降低旧任务和越权发送风险，但复查与发送之间仍可能发生权限变化。能否由渠道再次校验或通过最小化消息内容控制风险，须在真实系统中确认。

发送和打开都检查对象权限

建议 设置检查编辑权限，发送复查接收人访问权限，打开通知再次鉴权。消息尽量只放必要标识，日志不记录待办敏感正文；凭证复用现有秘密管理，不写入方案示例。

容量用参数估算后再压测

待确认 峰值领取需求可用峰值到期任务数除以允许处理窗口估算，再计入重试与扫描开销；记录存储量由每天任务数、保存天数和单记录大小计算。参数、允许延迟和余量尚未提供，不填写虚构 QPS。

建议 建议观察到期积压、调度延迟、取消率、渠道失败与 unknown 数量，压测应覆盖热点时间段和领取竞争，阈值需评审。

并发和部分成功必须单独验证

  • 建议 设置测试覆盖无权限、版本冲突、空截止时间与保存失败；规则未定的时间输入以待确认案例记录。
  • 建议 工作器测试覆盖重复领取、版本失效、待办完成、权限撤销、渠道超时、发送后宕机和 unknown 恢复。
  • 建议 通知入口回归覆盖历史通知与当前权限不一致。方案仅定义测试，未运行产品测试或压测。

兼容扩展后再开启发送

建议 建议先扩展表和兼容读取，部署关闭发送的代码，核对设置读写与任务生成，再对白名单开启。出现越权、重复或 unknown 增长时关闭发送，保留任务记录供对账；代码回退须兼容新表，不能直接删除发送记录。

待确认 真实开关、白名单范围、停止阈值、备份方式和回填规则待确认。不可逆通知无法撤回，数据删除不能当成回滚步骤。

契约确认是开发前置任务

建议 先确认业务和渠道契约，再并行实现设置与调度模块，最后联调权限、未知结果对账与发布开关。任务对应 DES-001、DES-002、DES-003；文件位置、负责人和工期尚未提供，不编日期。

渠道能力和竞态阻断实施批准

  • 待确认 需产品确认提醒时间、时区、重复规则、接收者和保存策略；这些决定影响数据契约与调度。
  • 待确认 需研发核验真实数据库条件更新、任务领取、渠道幂等与查询能力，否则不能承诺重复控制和自动恢复。
  • 待确认 需权限负责人确认复查和发送之间的竞态容忍边界及消息最小化；风险未解决时保持探索稿。
