# 技术方案设计

把需求转换为研发能够评审、拆分、实现和验证的方案。可落地意味着每项核心需求有明确实现路径、约束、失败处理、验收和发布前提，不意味着空缺信息已被猜定或文档等于已实施。

## 运行与交付约定

- 完整目录可由任何能读文件的 Agent 使用，所有资源相对本文件定位，无专属工具、企业账号或外部 Skill 依赖。
- 默认交付一份自包含 HTML 图文方案；Python 3.9+ 标准库辅助校验和渲染。无 Python 时，能写文件的 Agent 按规范直接生成内联 CSS/SVG 的 HTML，不要求安装依赖。
- 用户明确指定格式时遵循其要求；Word、PDF、在线文档需要宿主具备对应能力，不能把 HTML 偷换成交付格式。
- 仅分析用户授权的需求和代码范围，不执行生产查询、迁移、部署、压测、云端上传或产品代码修改。方案中的示例代码、SQL 和命令只是设计材料，未经明确要求不能执行。
- 仓库不完整、需求或现有技术栈不明时，先补关键信息。用户明确允许探索方案时可提出候选设计，保持“建议／待确认”，不能宣称生产就绪。

## 必读资源

起草前完整读取 [落地方案契约](references/design-contract.md) 和 [技术中文表达](references/writing.md)。配图前完整读取 [研发图表规范](references/diagrams.md)。执行脚本前读取源码或 `--help`。

[示例 JSON](assets/example.json) 与 [技术方案图文示例](assets/团队待办技术方案示例.html) 是虚构的提醒系统，用来展示粒度、九类图和状态标记。不得把示例栈、字段、接口或规则当成本次业务事实。

## 读取需求与现状证据

1. 完整读取需求、附件、设计和指定代码材料，保留原文版本和编号；找不到指定材料先请求有效路径或文件。
2. 将每个 `REQ-...` 的角色、前提、规则、异常、验收和确认状态登记。输入没有编号时分配稳定编号并说明对应原句，不替换已有编号。
3. 读取项目说明、依赖清单、关键模块、真实接口、模型、测试及配置；用文件路径、符号和版本记录证据，不凭文件名推断实现。
4. 写清“已核验的现状”“候选设计”“待确认的业务或技术决策”。已有接口与拟新增接口分开，候选库不冒充已安装依赖。
5. 会改变核心设计的缺口优先一次问清，通常不超过三个问题：需求来源与范围、技术栈和运行环境、规模与质量约束。探索方案可以保留缺口，实施方案遇到阻断项必须暂停对应结论。
6. 不把上游建议升级为确认。本技能可以直接接收需求文档，不必安装需求分析技能；同仓库串联时沿用其 JSON 或正文，逐项保留状态与来源。

## 与 PRD、开发阶段交接

端到端流程使用与 PRD 相同的任务目录。完整读取同仓库 `../product-development/references/handoff.md`（相对本技能目录），从本轮明确交接或清单读取本次真实 PRD，保留其编号、来源、状态和版本摘要，再生成权威技术方案（建议 `technical-design.json`）和图文文档。

用户要求后续开发时，用 `../product-development/scripts/pipeline.py register`（相对本技能目录）登记技术方案，并绑定生成时读取的 PRD 摘要；必须先登记 PRD。PRD 有变化或正文冲突，先重新评估而非强行登记。无脚本时按同一契约核验；只写技术方案时不依赖开发技能也不自动实施。来源或方案待确认保持原状态，登记不等于批准。

## 从约束选择最小实现方案

- 先写目标、非目标、既有边界和约束，再给推荐方案。优先复用现有能力，不默认微服务、消息队列、缓存或新数据库。
- 列出真正不同的替代方案和取舍：复杂度、维护成本、一致性、失败恢复、性能、部署约束、安全。没有证据不填伪精确打分。
- 记录关键设计决策：问题、选项、推荐、理由、成立条件、尚待核验项及不采用其他方案的原因。建议不等于评审通过。
- 建立 `REQ → DESIGN → TEST` 映射：每项需求关联模块、接口或数据变更、异常、验证及实施任务；每项设计能够回到需求，不扩展无关功能。

## 写清实现契约与失败路径

对每个设计项说明职责、输入输出、依赖、数据归属、实施变更和验证方式，至少覆盖：

- **架构与模块**：系统上下文、组件职责、边界、调用方向、复用和新增部分；逻辑组件不等于独立部署服务。
- **接口契约**：路径或签名、字段类型、必填和校验、认证授权、响应、错误、分页、版本兼容、幂等和重试。没有真实定义时拟议接口显式标记，不能杜撰成现有 API。
- **数据设计**：实体、键、字段、索引、约束、关系基数、读写路径、所有权、保存期限和删除。主键唯一与业务去重不是同一个保证。
- **核心机制**：事务边界、并发更新、顺序、去重、锁或租约、超时、重试、补偿与恢复；明确部分成功、宕机及竞态。异步发送不得空口保证 exactly-once。
- **前端与交互**：状态、错误提示、请求取消、重复提交、权限失效、可访问性；按需求适用，不硬加界面模块。
- **质量与安全**：认证和对象级授权、敏感数据、输入校验、秘密管理、日志脱敏、容量、延迟、可靠性、兼容与可观测性。安全内容仅用于合法系统防护设计。
- **容量**：输入量、峰值倍数、保留时长、消息大小、计算公式、余量和验证方法。没数据就写待确认或参数化公式，估算必须标输入来源和不确定性，不凭空承诺吞吐或预算。
- **测试与发布**：单测、契约、集成、并发、权限、失败注入及回归；数据迁移采用扩展—兼容—切换—收缩，描述备份、回填校验、回滚条件与不可逆部分。
- **实施拆解**：任务、前置依赖、变更位置、完成定义、责任角色和验收；工期、日期、人力未知不编。发布计划写开关、范围、指标、停止条件、回退与恢复责任。

## 绘制详细研发图

先选择图种，再依据同一套实体、接口、规则和需求映射绘图。每张图必须回答独立问题，标明标题、图种、确认状态、适用范围、需求编号、设计编号和读图结论。

内置渲染支持九种：`architecture` 架构、`flow` 流程、`sequence` 时序、`er` 实体关系、`state` 状态、`dataflow` 数据流、`deployment` 部署、`dependency` 研发依赖、`swimlane` 泳道。

- 默认核心组合是架构、关键时序和数据/状态图；按真实需求追加流程、部署、数据流和研发依赖，不为凑九张强画不适用图。
- 每种适用图都应详细：关系名、条件、请求/响应、实体字段及基数、状态守卫与副作用、信任/部署边界、任务前提；含失败、取消或回退分支。
- 详情与质量预算见 `references/diagrams.md`。复杂图拆为概览和局部，不压成小字或省掉关键连线。
- 图中现状和新增、建议和确认分别可辨。图只是机制示意，不冒充当前基础设施拓扑或官方图。
- 不交付裸 Mermaid、ASCII 或未经渲染的代码充当图；图表依赖不联网，正文和图内字段、状态及关系必须一致。

## 通俗表达融入方案，不降低精度

分析与润色分开，起草后再执行 `references/writing.md` 的三遍回读：

1. **保真**：数字、字段、术语、状态、事务边界、条件、否定、因果、重试和承诺不变。上游待确认不能润色成已确认。
2. **易懂**：先用一句平实中文说明“为什么需要、谁负责、如何工作、失败怎么办”，再给精确接口或机制；术语首次解释，后文保持同一名称。少用空心“赋能、全链路闭环”等词。
3. **节奏**：检查模糊指代、重复小结和无停顿长句，优先补停顿，严谨约束不为口语而拆坏。

术语保留原词，解释可以补，但只解释已有设计含义，不新增机制。示例代码和 API 字段不做语言清洗。已经准确清楚的句子保留，不因“去 AI 味”删除真实风险、编号或技术边界。

## 生成、核验与交付

默认方案数据契约见必读 reference。按实际路径替换占位并引用含空格路径：

```bash
python3 <技能目录>/scripts/check.py <技术方案.json>
python3 <技能目录>/scripts/render.py <技术方案.json> --output <技术方案.html>
```

校验结构错误须先修复；表达提醒由 Agent 结合上下文判断，脚本不自动改稿。默认拒绝覆盖，只有用户要求更新自己的生成产物时使用 `--force`。Windows 可用 `python`。

交付前用独立方式回读，核对所有需求映射、设计、测试和图引用；实际查看桌面、窄屏、图内箭头、标签、滚动和末尾。打印需求存在时抽查分页。规范生成不代表现状、业务、性能或生产运行已验证；无运行证据时明确缺口。

完成门槛：核心需求都有设计和可观察验证；关键决策有依据或阻断标记；正常与异常闭合；迁移和回退可执行条件明确；正文、图、代码一致；不编造现状、工期和测试结果。对未解决阻断项交付探索或待评审方案，不能声称实施批准。

给用户文件、路径、打开方式、文档状态、关键取舍与待确认项，以及真实完成的验证。仅交付完整方案，不只给提纲。不要自动实现、迁移、上线或提交仓库。
