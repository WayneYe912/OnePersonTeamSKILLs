# 用例设计、类型与风险

## 类型选择

按真实 PRD 选择，不为了数量机械扩展。至少考虑核心功能、边界、异常和权限；不适用的类别写理由。非功能规范缺失可列为待确认，不编阈值。

- **functional**：业务正常路径、输入输出和副作用，结果是可观察的成功条件。
- **boundary**：已给范围的端点、端点内外、空和最小值，注明包含/不包含；数字来自 PRD，不猜。
- **negative**：非法输入、缺失字段、超时或业务拒绝，核对错误与未发生的副作用。
- **permission**：登录、角色、对象级可见/可写、权限撤销和跨角色隔离，只用授权测试账号。
- **security**：合法系统防护验证，如输入校验、敏感输出与秘密保护；不生成越界攻击步骤，不自动运行。
- **api**：PRD 有接口契约时验证字段、错误、版本与幂等；未给实际接口不编路径和错误码。
- **state**：已定义状态与允许/禁止迁移、条件和副作用；未知结果不可当失败。
- **compatibility**：给定设备、浏览器、版本、数据格式兼容；缺范围保持待确认。
- **accessibility**：键盘操作、焦点、可读提示、非纯颜色信息；标准和例外有依据，不能只列“支持无障碍”。
- **performance**：给定负载、数据量、计时边界、百分位/成功率和阈值；目标没给时不是可执行验收。
- **reliability**：依赖故障、取消、恢复、部分成功与重复，按 PRD 的可观察后果测试，不杜撰实现机制。
- **regression**：既有功能与修订影响范围，必须有基线/旧规则依据，不标所有用例为回归。
- **acceptance**：从用户目标出发的完整场景，含真实输入、动作和成功/失败结果。

## 层级与方法

层级：unit、integration、system、acceptance。PRD-only 默认系统/验收更容易确定，单元与模块接口需可选设计或代码依据；不要虚构代码位置。

方法：scenario、equivalence、boundary_value、decision_table、state_transition、pairwise、error_guessing。说明选择条件和覆盖的类别/迁移/组合，不用方法标签替代实际用例。

成对组合不是全部组合覆盖；决策表必须列条件与动作，避免互斥条件被写成同一路径。边界方法明确规则端点，异常猜测需要风险理由。规则冲突或空缺时请求确认，不用常见产品习惯填默认值。

## 粒度与数据

每条用例验证一个清楚目标；长流程可多步，但每步可观察。共享前提可以引用文字定义，具体账号仅用匿名角色，不带真实用户身份。数据注明准备方式、前置状态、隔离与清理，不能用“任意有效数据”掩盖不可复现。

未知值可写“待确认”，但 `definition_status` 必须同步待确认；这类不能计为可执行覆盖。已确认规则不改变程度、否定、单位、端点和身份。PRD 中建议保持建议或待确认，不升级为确认。

## 覆盖与优先级

逐项建立需求 → 测试条件 AC → 用例 TC。每个条件至少有用例或 coverage_gaps；缺口说明原因和需要补的依据，不填虚假用例凑覆盖。

P0/P1/P2 用实际风险和影响理由，权限泄露、核心中断优先，但不是每个安全类别自动 P0。测试映射、可执行定义与执行结果分开统计。结构校验只证明编号存在，不判断规则等价、用例充分或实际测试成功。

## 评审与收尾

读完整 PRD，再读用例，双向检查：每条预期可回到规则/已标建议，每条核心规则有测试或缺口；没有新增承诺或遗漏例外。

检查重复目标、虚假错误码、无依据性能指标、不可准备数据、仅“成功”的断言和被隐藏的待确认。把模糊表述改成可观察结果；不能凭润色添加业务机制。通俗中文保持技术术语和事实，原话、编号、数字、代码和来源不动。

用户只要设计时不执行产品测试；若后续明确要执行，由开发/测试能力先核对环境、范围、可用接口与权限并另记运行结果。初始用例设计统一未执行，不填“通过”。
