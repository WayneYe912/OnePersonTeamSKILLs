# 文档结构与数据契约

## 文档的阅读顺序

先让评审者知道要解决什么、哪些决定尚未确定，再读方案和具体规则。默认保留以下内容；没有材料时明确缺口，不用空话填满章节。

- **概览**：原话、需求复述、目标、文档状态与阅读提示。
- **用户与场景**：角色、问题、触发条件、现有做法。画像和现状只用已有材料。
- **范围与优先级**：本期、后续候选、不做；建议优先级及理由。
- **推荐方案**：方案如何解决问题、成立条件、关键取舍。可在这里插主流程图。
- **功能需求**：逐项编号、业务规则、异常和验收；渲染器单独生成这一章。
- **业务规则**：跨功能权限、状态变更、重复操作、冲突和例外。
- **数据与权限**：关键字段、可见范围、保存与删除、审计；没有涉及数据也说明判断。
- **质量要求**：性能、兼容、可访问性、安全等相关约束。缺阈值写待确认。
- **发布与衡量**：指标口径、发布前提、回退、观察方法。不得捏造工期和目标值。
- **风险与依赖**：风险触发条件、后果、处理办法和待谁确认；未知负责人不编名字。
- **待确认事项**：问题、影响、阻断范围和需要谁决策；已解决的问题不重复列出。
- **信息来源与校验**：原话、材料、外部证据和完成的检查；区分事实与设计建议。

简单需求可合并章节，但不能漏掉有意义的边界和验收。渲染器采用下述统一结构，保证第一次阅读即可找到信息。

## JSON 根结构

使用 UTF-8、标准 JSON，不含注释或尾逗号。数字和字符串按实际类型填写。以下为字段说明，不是可以直接交付的空模板。

- `title`：非空的具体标题，如“团队待办到期提醒需求分析”。
- `original_request`：用户原话，原样保留。
- `status`：`探索草稿`、`待评审` 或 `已确认`。只有用户确实确认全部内容才能写已确认。
- `summary`：非空字符串，一段说清用户、问题、方案方向与当前边界。
- `sources`：至少一项，字段为 `id`、`title`、`note`，可选 `url`。原话可编号 `SRC-001`，没有 URL 就不编；URL 只允许真实 `https://` 或 `http://` 来源。设计提案不是证据。
- `sections`：章节数组，每章有 `id`、`title`、`blocks`。默认 id 依次为 `users`、`scope`、`solution`、`rules`、`data`、`quality`、`rollout`、`risks`、`questions`，这些 id 不得遗漏或重复。标题按实际内容命名。
- `requirements`：至少一项，结构见下文。
- `visuals`：默认至少两个，结构见下文。视觉类型仅支持 `flow`、`wireframe`。

数组和字符串不接受空内容充数。参考 `assets/example.json` 看完整、可运行的例子。

## 章节内容块

`blocks` 必须为非空数组，每块为以下之一：

- 段落：`{"type":"paragraph","text":"内容","status":"建议","source_ids":[]}`。
- 要点：`{"type":"list","items":[{"text":"内容","status":"已确认","source_ids":["SRC-001"]}]}`。

段落和每个列表项的 `status` 必填，只允许 `已确认`、`建议`、`待确认`。`source_ids` 是来源 id 数组；已确认内容必须有来源，建议和待确认可为空。来源有编号仍需人工核对其是否真的支持该句，工具只能检查引用存在。

待确认事项章也用上述块。没有待确认事项时说明确认范围和依据，不写空数组。不能把已确认标记只放在整章顶部，掩盖章内建议。

## 单个功能需求

必填字段：

- `id`：`REQ-001` 格式，至少三位数字，全篇唯一。
- `name`：直接说明操作或能力。
- `status`、`source_ids`：同章节内容块的状态与来源约定。
- `priority`：`P0`、`P1` 或 `P2`。
- `priority_status`：`已确认`、`建议`、`待确认`；优先级不是功能确认状态。
- `priority_reason`：排序理由，禁止把“重要”当理由。
- `actor`、`precondition`、`trigger`、`response`：角色、前提、操作、系统响应，均为非空字符串。
- `rules`：非空字符串数组，写可判定的条件和规则。
- `exceptions`：非空字符串数组，至少涵盖一个真实异常及恢复办法。
- `acceptance`：非空数组，每项含非空的 `given`、`when`、`then`。

需求条目内的规则和验收继承该条目状态。不能在“已确认”条目里夹带未确认的规则；拆为另一个待确认条目，或把整条降为建议。优先级已确认时同样必须有来源支持。禁止为通过校验编造内容。

## 图文结构

所有图必填 `id`、`title`、`caption`、`status`、`source_ids`、`req_ids`。id 使用字母开头的字母数字、短横线组合，全篇唯一；`req_ids` 至少关联一个现有需求。`status` 与来源约定同正文，图的整体状态与节点状态均可辨认。

### flow

用于流程、状态迁移或角色关系：

- `type`：`flow`。
- `nodes`：至少两个节点，每个有 `id`、`label`、`status`、`source_ids`。
- `edges`：至少一条有向关系，每条有 `from`、`to`、`label`、`status`、`source_ids`，端点必须是本图节点 id。

渲染器按输入节点顺序纵向排布。相邻节点的正向关系画在节点间，分支和回边分配右侧路线，方向用箭头、条件用文字显示。节点顺序不自动推导连线；必须显式给出真实关系。图中可以有回边和分支；超过八个节点优先拆图，不能删除业务分支来凑布局。

### wireframe

用于低保真界面结构：

- `type`：`wireframe`。
- `screen_title`：非空。
- `fields`：非空数组，每项有 `label`、`value`、`note`，均为非空字符串。
- `actions`：非空字符串数组，描述可见操作。

`value` 是标明用途的显示示例，不代表实际业务数据；真实默认值及枚举须在业务规则中说明。图形标为低保真示意，操作使用无交互外观，不做虚假可点击按钮。

## 安全、运行和失败行为

所有自由文本按纯文本处理，渲染器转义 HTML。正文不接受原始 HTML、脚本或远程图片；图形用确定性内联 SVG/CSS，无 CDN、网络请求、JavaScript 或构建依赖。来源链接校验协议并转义。

渲染器先完整校验，再用独占创建方式写文件；目标存在时拒绝覆盖。`--force` 仅用于用户要求更新。错误输出到 stderr，退出码 2；不会生成“半份文档”代替正确结果。

检查器把疑似半角标点、名词化、套话、重复及过长无停顿片段列为建议，带字段路径。正则不能理解语义，也不能保证零误报；绝不自动替换代码、原话、专业词或引用。
