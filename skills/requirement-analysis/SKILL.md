# 一句话需求分析

把“想做什么”写成产品、设计、研发和测试能共同评审的文档。详细体现在规则、边界和验收明确，不体现在字数多。默认用中文，保留用户原话和专业术语。

## 执行约定

- 这是标准 `SKILL.md` 技能目录，使用相对路径。先定位本文件所在目录，后续资源都相对于此目录解析，不能假设当前工作目录就是技能目录。
- 核心能力由 Agent 阅读并执行，无指定模型、工具名、MCP、企业账号、绝对路径或外部 Skill 依赖。
- 默认产物为一份自包含 HTML 图文文档，浏览器离线可读、可打印；有 Python 3.9+ 时使用内置渲染器。Python 是渲染辅助，不负责推理。
- 用户明确要 Word、PDF、在线文档或 Markdown 时，遵循其格式；用所在环境支持的能力写入真实图形，不能交付未渲染的图表代码冒充图片。不能生成指定格式时说明限制，不静默换成 HTML。
- 用户未授权时，不把需求、个人信息或业务材料上传到外部服务，不创建云文档、不发布、不安装依赖、不修改产品代码。

## 必须读取的资源

起草前完整读取 [文档结构与数据契约](references/document-contract.md) 和 [中文表达优化](references/writing.md)。配图前读取 [图文规范](references/visuals.md)。首次使用渲染器时读取其源码或运行 `--help` 确认参数。

[示例数据](assets/example.json) 是虚构的团队待办需求，学习拆解粒度、标注方式和图文组织，不能把它的业务规则套到新需求中。[渲染示例](assets/团队待办需求分析示例.html) 可直接用浏览器打开，查看最终阅读效果。

## 从输入到交付

### 理解需求，先确定分析对象

1. 读取全部原话、附件和指定参考，检查是否可访问；不能用印象补齐缺失文件。
2. 写一句需求复述，说明谁在什么场景下遇到什么问题，想获得什么结果。区分目标和用户提出的解决手段。
3. 建立信息台账：用户已给的事实、需要核验的外部事实、Agent 提出的建议、仍未确定的业务决策。每项有来源或状态。
4. 判断缺口是否改变核心方案：目标用户、所在产品、核心业务规则、权限和敏感数据边界、成功条件属于关键缺口。最多一次提出 1–3 个必要问题；现有材料已经回答的不再问。
5. 关键缺口未解决时暂停受影响部分，不擅自选业务方向。用户明确要求“先做探索草稿”时可以提出方案，但必须标为建议或待确认，不能写成既定需求。配色、文件名等低影响选择自行处理。

### 拆解用户问题与范围

- 描述现状、具体阻碍和目标；没有现状数据时写“尚未提供”，不用虚构用户访谈、竞品结论或增长效果。
- 梳理主要角色、使用场景、触发条件、输入、操作和预期结果。
- 区分本期范围、后续候选和明确不做；不把一句话膨胀为账号体系、推荐系统或完整业务平台。
- 给出推荐方案和成立条件。只有确有不同取舍时列备选，不为凑数量列方案。
- 指标写清定义、分子分母、采集方式和观察周期。基线、目标值没给就留“待确认”，不要自己承诺提升比例。

### 把功能写成可验收的契约

给每个需求稳定编号 `REQ-001` 等，至少说明：名称、状态、优先级及理由、角色与前提、触发操作、系统响应、业务规则、异常处理、验收标准。

- 状态逐项区分“已确认／建议／待确认”。优先级也有确认状态；建议排序不能冒充团队排期。
- 写出正常、空态、加载、失败和无权限场景；按实际需求补重复提交、并发修改、超时、取消、恢复、删除等，不机械地给每项堆全套异常。
- 每条验收包含“给定／当／则”，预期结果可观察。只写“体验流畅”“支持该功能”不算验收。
- 字段说明名称、类型、必填、约束、默认值来源和错误提示；规则缺失保持待确认。
- 涉及数据时写所有权、可见范围、保存期限、删除与审计。涉及 AI 时补输入输出边界、失败回退、人工确认、评估与敏感信息处理；不承诺模型永远正确。
- 性能、可访问性、兼容、安全等非功能约束按场景列出；具体阈值必须有来源或建议标记。
- 不替研发编接口、架构、工期或成本。不确定的技术方案列为待研发评估。

### 让图真正帮助理解

默认至少绘制两个回答不同问题的图：主流程图，以及界面示意、状态迁移图或角色关系图。简单需求可精简，用户明确只要文字时不强行配图。

- 先确定节点、角色、状态与关系，再作图。每个关键图关联需求编号，正文和图使用同一份规则。
- 流程包含起点、结果及核心异常分支，连线写明动作或条件。
- 界面示意标注“低保真示意”，说明字段、操作和状态；不是最终设计，也不冒充现有产品截图。
- 规则未确定的分支在图中同样标“建议”或“待确认”；禁止只在正文承认不确定、图中却画成已确认。
- 图下附一句读图说明。说明图揭示的取舍或分支，不照抄所有节点。
- 不用装饰性插图、未加载的远程资源、纯文本箭头或未执行的 Mermaid 满足图文要求。

### 成稿后独立优化表达

需求分析阶段可以产生明确标注的建议；文本优化阶段只改说法，不能再新增信息。执行以下顺序，具体判据见 `references/writing.md`：

1. 通读整篇，理解主线及各段作用，不逐句“翻译”原稿。
2. 锁定原话、数字单位、术语、需求编号、状态名、条件范围、因果方向、模态和承诺。
3. 扫标点、句式、词汇、段落结构和凑数式排比。优先去空架子、重复小结、模糊指代及无依据的拔高。
4. 把“进行配置”写成“配置”，使用真实动作；把已有具体规则放到前面。原稿缺数字或场景时提醒补充，不编一个显得更生动。
5. 分三遍回读：事实与契约保真、冗余和翻译腔、句间节奏。先补自然停顿，只有独立信息挤在一句时才拆句。
6. 好句子不为改而改。保持需求文档的专业书面语，不把“幂等”“回滚”“可访问性”替换成含糊大白话。
7. 保留有用途的目录、表格、编号和真实风险；去 AI 味不能破坏评审导航和严谨边界。

### 生成与验证

有 Python 时，把完整分析写成符合契约的 UTF-8 JSON，再执行：

```bash
python3 <技能目录>/scripts/render.py <需求数据.json> --output <需求分析.html>
python3 <技能目录>/scripts/check.py <需求数据.json>
```

将尖括号路径替换为真实路径并正确引用含空格的路径。Windows 可使用 `python`。运行目录不限；无需 pip、npm 或联网。输出存在时默认拒绝覆盖，只有用户要求更新同一产物才使用 `--force`。

`check.py` 输出 JSON 检查报告：结构错误阻断，表达建议不自动改稿。退出码 `0` 表示结构检查通过，`1` 表示结构不合格，`2` 表示读取或参数错误。报告不代表业务真实性或语义等价已验证。

无 Python 但可写文件时，Agent 按同一契约直接生成内联 CSS/SVG 的自包含 HTML；不要求用户安装工具。无文件写入能力时输出完整正文及宿主支持的已渲染图，并明确说明没有生成独立文件。图形不可渲染时不能声称完成图文文档，说明能力缺口。

交付前实际打开或渲染文件，检查桌面和窄屏：标题、图文、流程连线、界面示意、长表和文档末尾不能空白、重叠或裁切。宿主有文档验证能力时优先使用；否则用浏览器检查并记录范围。结构通过不等于视觉通过。

### 交付给评审者

简短说明文件名、路径、打开方式、文档状态、关键待确认事项和验证范围。不要把脚手架或写作提纲当成成品。

最终核对：

- 原话与来源保留，所有建议和待确认项可辨认。
- 每个本期需求有可观察验收，主流程和异常能闭合。
- 图中的节点、状态和编号与正文一致。
- 优化前后的事实、规则、否定、范围和承诺未改变。
- 未编造数据、用户研究、优先级共识、接口或排期。
- 真实产物可读；未完成项已说明，不夸大验证结论。
