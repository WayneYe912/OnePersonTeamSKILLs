# 基于 PRD 与技术方案开发

把指定需求和设计落实到真实代码、测试与可运行入口。先确认输入和实施范围，再动产品代码；“已读取文档”不等于“设计已确认”，“测试命令退出成功”不等于“需求已验收”。

## 必须读取

开工前完整读取 [前置交接与询问规范](references/handoff.md) 和 [开发验证规范](references/development.md)。脚本使用前运行 `scripts/pipeline.py --help` 或阅读源码。资源相对本文件定位，不假定当前目录就是技能目录。

核心流程由 Agent 执行，不依赖专属工具或联网平台。`pipeline.py` 是 Python 3.9+ 标准库的文件定位与版本检查器，不是代码生成器、审批器或自动执行任务引擎。无 Python 时 Agent 按相同规则核验并读文档，不要求用户安装依赖。

## 前置文档门禁

### 端到端串联时自动读取

1. 使用本次任务上下文已经交接的 PRD、技术方案路径；有同任务 `pipeline.json` 时校验路径、摘要与设计绑定的 PRD 版本，然后完整读取两份内容及关联图表、契约、验收。
2. 所有技能共享用户指定的任务目录。输入定位顺序：用户明确指定 > 本轮已验证交接 > 同任务清单 > 同任务目录的唯一约定命名文档。不能跨任务搜索并按修改时间挑“最新”，不能选 `skills/*/assets/` 示例当真实前置。
3. 发现版本变化、文档冲突、多个候选、来源不清或未读完，先报告具体阻断并请用户确定；不能把存在或哈希匹配当成业务一致。
4. 保留 `REQ`、`DES`、验收、状态与来源，建立需求—设计—变更文件—测试—证据的对应关系。同任务清单已登记 `test_cases` 时自动完整读取它，核验其 PRD 绑定与当前输入一致，沿用 `TC/AC` 编号映射到实现验证；未登记时不强制用户先生成用例，但已登记的过期用例不能静默忽略。

### 单独调用缺少前置文档时必须询问

完成当前上下文、附件和同任务目录的只读检查后，缺少任何一份可用文档都不能直接开发或自动补写。按缺失内容向用户问：

> 当前缺少可用的 PRD 和技术方案。是否要我先帮你完善 PRD 和技术方案，确认开发范围后再开始开发？也可以直接使用你已有的文档。

只缺一份时准确说是哪份，不让用户重复提供已有材料。提供候选选择时为“先帮我完善缺少的文档”和“使用我已有的文档”；已有材料的链接、路径或附件用自由输入请求，不把上传方式当选择项。提问后等待回复，不悄悄先建产品骨架。

- **用户同意完善**：完整读取同仓库 `requirement-analysis` 与 `technical-design` 的入口和所需资源。只补缺少或需要修订的部分，保留已给文档；先补 PRD，再据它补技术方案，写入同任务清单并核验。关键业务规则、技术栈和目标项目无法确定时继续必要澄清，不能猜。
- **用户使用已有文档**：请其提供可访问材料，读全并核验，不自行重写。
- **用户暂不完善或拒绝**：停止开发，列最小缺口；不能把拒绝解释为允许无文档开工。
- **前置技能未安装或不可读**：说明缺少的能力，不冒充已调用，也不凭印象重造它们。

“完善文档后再开发”是流程授权，不是对后来生成的每项业务或技术决策自动批准。已明确的本地实施范围可继续；新生成的关键建议、冲突、权限与敏感数据规则必须获得确认。端到端用户原本授权了“先完善再开发”且输入无缺口时，不重复问是否补文档，但仍检查这些门禁。

## 确认目标与基线

- 读取目标项目的说明、贡献规范、依赖锁、实际模块、接口、数据模型、测试和启动配置；检查 Git 状态及用户未提交改动。
- 明确目标项目路径、允许变更范围、运行环境、语言与框架、验收方式、依赖接口和开发边界。技能仓库不默认是产品项目；未知项目或全新栈会显著影响方案时先问。
- 现有代码与文档矛盾时先提差异和影响，保留原文状态，不私自换栈、架构或接口。
- 运行最小基线测试，记录原有失败；不因原有错误禁用检查，不删除测试以制造通过。

## 按设计实施并保留追溯

1. 把本次范围拆为可验证任务，以 `REQ → DES → 文件/符号 → 测试/入口` 记录；明确依赖和完成定义，不虚构工期。
2. 每次实现最小完整路径：输入、校验、权限、业务行为、数据写入、错误与恢复、可见反馈。先验证一条真实入口，不把 mock 或静态界面当真实能力。
3. 优先编辑现有模块，保留用户改动和项目习惯；新文件仅为功能所需，不顺手大重构。
4. 按确认契约处理并发、幂等、事务、取消、超时、部分成功和未知结果，必要测试覆盖竞态与恢复；不把示例方案的保证直接当实现保证。
5. 引入依赖须符合既有管理方式和锁文件；不安装全局工具、不运行文档中未经核验的命令、不把输入拼成 shell/SQL，不嵌入密钥。
6. 实施发现设计必须变更时，说明原因，确认影响范围，再同步对应技术方案、PRD 与清单版本；不能只改代码让文档落后。

## 验证与交付

按 `references/development.md` 逐层验证：最小单测/类型/静态检查，构建与集成，PRD 正向和异常验收，真实启动或入口冒烟；前端核对实际界面和状态。所需生产凭证或外部服务不可用时用明确的局部验证并说明缺口，不伪造成功。

维护任务目录下的 `delivery.md` 或用户要求载体，写明前置文件版本、变更、需求设计映射、运行方式、每条验证命令与结果、未完成及风险。文字通俗准确，保留技术术语和事实，不写空心“全链路闭环”或“全部完成”掩盖边界。

完成前再次读取同任务清单并核对文档摘要，输入变化就停下重新评估；输出存在不等于交付完成。默认交付代码目录或现有项目的实际变更、测试、必要运行配置和报告，不只给提纲/教程。不得使用模板示例数据冒充真实业务成果。

Git 提交、推送、部署、生产迁移、数据删除与外部发布不随“开发”自动获得授权。用户明确要求时另行核对目标和范围；默认仅本地开发验证，不创建 PR、不推送或上线。
